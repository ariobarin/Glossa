# Glossa 0.2.5 release review

## Scope and baseline

This is a patch-release proposal, not permission to publish. The starting npm package and native release are `@ariobarin/glossa@0.2.4`, tag `cli-v0.2.4`, source `6055b4ecdedc4dac21b8766a5fbd279fa1135256`. The audited main and hosted-relay source is `e1a638c1745aef9804865b98006e154db9744229`.

Those baselines are different: the hosted relay already has later fixes, while the published CLI does not. The tag-to-main diff contains 79 files, 2,864 additions and 2,740 deletions. No package rename, Node runtime downgrade, mandatory local command approval, model integration, conversation store or protocol-negotiation replacement belongs in this patch.

Review the focused pull requests before the version change. Use `dev/0.2.5-candidate` only as the combined verification branch. Its package-script conflict resolution keeps both the packaged CLI smoke and the update-notice smoke. The final verification record belongs in the release PR and must name the tested commit. Do not merge the candidate as a substitute for reviewing the individual changes.

## What changes

| Area | Reason and consequence |
| --- | --- |
| Activity retention | Keep 256 recent rows and 1 MiB of serialized invocation metadata in one bounded list. Retain in-flight rows, expire old details, own bounded summary strings and clear stale selection state. This deliberately replaces the former 9,999-row/16-MiB UI budget; it does not add persistent history. |
| Command retention | Clear expiry timers when completed command records are evicted, rather than letting a five-minute timer accumulate for every completed command. The eight-record cap now also bounds those timers. |
| Command cleanup | Bound cleanup attempts and pending pipe closure. Signal POSIX process groups after leader exit. On unconfirmed Windows cleanup, return an explicit failure and disable further starts in that worker instead of hanging or reporting false cancellation success. Natural exit racing termination must not poison the worker. |
| Agent contracts | Remove duplicate dispatch/result code and repeated instructions. State actual file, range, image and search limits; distinguish missing results from incomplete searches; explain safe recovery after stale revisions and uncertain mutations. |
| Result compatibility | Return complete JSON text alongside structured content, including results over 16 KiB. This restores compatibility for clients consuming text only, at the cost of larger responses for clients retaining both forms. Image bytes remain native MCP content, not duplicated in structured metadata. |
| Update awareness | Remember a validated available version, so the daily check does not suppress the reminder on subsequent starts. Preserve offline fallback, disabled checks and version/channel invalidation. No daemon, telemetry or new automatic-update default is added. |
| Release verification | Fix the obsolete help assertion and test the built npm entrypoint before release day. Add manual six-target native verification with publishing explicitly disabled on manual runs. Test the embedded runtime's regex/glob subprocess behavior and the real direct installers. |
| Windows installation | Download binaries without HTML parsing or per-chunk progress rendering; use finite HTTP timeouts. Run installer tests noninteractively with a process deadline. |
| Dependencies | Keep the compatible `fast-uri` 3.1.8 security fix separate from the existing `ip-address` 10.7.2 update in #288. Do not replace either with an unrelated major upgrade. |

The public MCP contract becomes `3.2.0`; the CLI package becomes `0.2.5`. Tool names, argument shapes, result schemas, security annotations, access profiles and rolling compatibility with pre-image workers remain intact. Refresh or rescan the connector after the reviewed relay metadata is deployed. A successful CLI release is not an approval of a marketplace submission.

## Kevin's Activity proposal, PR #289

The proposal addresses a real cost: retaining and repeatedly scanning a large interactive history. Its bounded cache and disk-backed browsing are useful for a product that wants durable, full-session history. They are not necessary to bound Glossa's current Activity display.

The reviewed implementation adds a JSONL journal plus disk index, retains command arguments and output/file previews after exit, and has no overall disk rotation or lifetime limit. Synchronous disk errors also become a reason to disconnect the worker. This changes the existing no-content-persistence policy and introduces disk-capacity, retention and failure cases in exchange for a UI feature.

The replacement keeps one bounded in-memory list and no new persistence layer. It supersedes the memory-control purpose only, not full-session or post-exit browsing. Keep #289 open until that product tradeoff is explicitly reviewed; do not label the two implementations functionally equivalent. A local synthetic comparison of 20,000 Activity events measured median times of 4.63 seconds for the old 9,999-row implementation, 0.99 seconds for an intermediate map-based alternative, and 0.14 seconds for the final 256-row list. These are fixture results with different retention budgets, not general application speed guarantees.

## Risk-based verification

The normal suite remains a few hundred named tests. The 100,000-read soak is opt-in, not part of every pull request. Existing permission, ownership, secret suppression, path/link, deadline, buffer and waiter-release tests remain necessary; the soak does not replace them.

Run the combined candidate, not only each branch:

```sh
npm ci
npm run check
npm run integration:local
npm run test:soak
npm audit
npm pack --workspace @ariobarin/glossa --dry-run
```

`integration:local` creates its own loopback-only Docker Postgres instance and synthetic identity environment. It exercises real signed OAuth, MCP HTTP, database storage, the built relay and built CLI, pairing/revocation, account and profile boundaries, guarded mutations, native image content, hostile regex/glob deadlines, command concurrency, output ranges, cancellation and shutdown. It never needs a production account, live keyring or user files. See [integration tests](../integration-tests.md) for exact fixtures and limits.

The worker soak performs 1,000 warmup and 100,000 measured reads of a 1-MiB file, split between whole-file and ranged operations. It also runs 60 dual-stream commands and waits through actual five-minute record expiry under a 96-MiB old-space limit. It samples post-GC heap, RSS, external memory and ArrayBuffers, with growth, plateau and absolute limits. Deliberately retaining file results was verified to fail the heap-growth check.

The initial completed soak kept heap near 12.6 MiB; peak measured RSS was about 123 MiB. ArrayBuffers fell from about 16.33 MiB to 0.024 MiB after expiry. Record the final candidate's measurements separately rather than presenting these initial measurements as evidence for an untested revision.

Finite tests establish particular bounds and release paths, not that all OOM failures are impossible. In-process worker measurements are not 100,000 HTTP requests, relay memory measurements, multi-day packaged-HUD observations or four-model agent evaluations.

Native verification is separate from ordinary PR CI:

```sh
gh workflow run publish-cli.yml --ref dev/0.2.5-candidate
```

Inspect the exact workflow commit, all six platform results, and both publishing jobs. `publish-release` and `publish-npm` must be skipped on manual runs, even on a tag. The native matcher fixture tests candidate source inside the actual executable's embedded runtime; the normal CLI smoke separately exercises its compiled entrypoint. This is not a full native-binary MCP integration run. See [releasing](../releasing.md).

## Large files and simplification decisions

The audit treated 500 lines as a review trigger, not a reason to split code mechanically. The MCP owner fell from 1,124 to 738 lines, with small result and copy modules and a net reduction across their owning source. Its tests also became shorter through shared, meaningful cases. The Activity model fell from 538 to 490 lines after removing duplicated formatting and parallel retention indexes.

Other large owners include the HUD (1,779 lines), filesystem service (1,527), HTTP routes (877), protocol schemas (757), managed session (609), remote worker (582), HUD preview (519) and panel (503). These were inspected for responsibility, repeated work and boundary risk. A broad rewrite of filesystem canonicalization, atomic writes or routing would increase this patch's risk without a demonstrated benefit. Keep those boundaries coherent; extract a separately testable responsibility only when it removes duplication or isolates a real lifecycle. The new platform termination helper follows that rule.

Not every source file is below 500 lines, and adding real integration fixtures increases total repository lines. Track production-code simplification separately from test/documentation additions rather than claiming a net repository reduction that did not occur.

## Research applied to the agent surface

The reviewed OpenAI Astra and Anthropic Fable 5, Fable 5.1 and Opus 5.5 guidance supports precise task scope, necessary context and useful constraints rather than accumulated generic reasoning recipes. This does not justify weakening permissions or removing all agent verification. Reasoning effort, model selection, context compaction and agent loops belong in the host, not this bridge.

After review, the server context describes workspace access rather than prescribing a workflow. Tool descriptions state capabilities and limits; errors report the failure and any necessary next step. Permission and credential checks stay in code. The client can use local tools for general questions too. No controlled cross-model success-rate improvement is claimed.

Primary guidance: [Astra prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra), [Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5), [Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1), [Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5), and [MCP structured-result compatibility](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content).

Practitioner examples were treated as examples, not benchmarks: [Simon Willison's shadow-root experiment](https://simonwillison.net/2026/Sep/23/shadow-roots/) illustrates short outcome-oriented instructions; [Armin Ronacher's long-running Astra experiment](https://lucumr.pocoo.org/2026/9/7/astra-why/) cautions against equating unattended runtime or code volume with quality.

For CLI updates, [Claude Code setup](https://code.claude.com/docs/en/setup) and [Codex CLI guidance](https://developers.openai.com/codex/cli) were comparisons, not templates to copy. Glossa already had channels, daily checks, explicit update commands, disabled/notify/auto policies and active-session update locks. The missing behavior was a reminder that survived a second start. [PowerShell's binary-download guidance](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/invoke-webrequest?view=powershell-5.1) also supports avoiding HTML parsing for installer downloads.

## Approval boundary

Review memory/history tradeoffs and the command cleanup limitation explicitly. Merge only reviewed changes with passing checks, rerun the combined verification after any edits, then apply the version change. Publishing a `cli-v0.2.5` tag, deploying the relay and refreshing connector metadata are separate, approval-dependent steps. No test result authorizes those actions by itself.
